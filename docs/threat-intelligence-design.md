# ThreatLenz Phase 4: Explainable Threat Intelligence & Risk Prioritization
**Technical Architecture, Governance, and Implementation Specification**

---

## 1. Executive Summary & Architecture Scope

### 1.1 Objective
Phase 4 elevates the ThreatLenz platform from basic statistical and machine learning flow classification (Phases 1–3) to an **explainable, contextualized, and prioritized threat intelligence system**. It transforms classified flow aggregates into structured, actionable threat event profiles mapped to standard security frameworks and prioritized by an explainable multi-factor scoring model.

### 1.2 Boundary & Architectural Principles
- **Dataset Realities:** ThreatLenz operates over the curated CSE-CIC-IDS2018 dataset (`data/processed/flows.parquet`). The data represents emulated enterprise lab traffic, not real-world IoT device captures or confirmed exploitation traces. IP addresses were stripped during dataset creation, and host-level telemetry is absent.
- **Strict Decoupling:** Phase 4 generates structured in-memory profiles, JSON models, and evaluation routines. It strictly avoids coupling to future persistence engines (PostgreSQL/TimescaleDB), API routes (FastAPI), or user interface components (Angular).
- **Zero Destructive Actions:** Advisory recommendations generated by ThreatLenz are strictly defensive and non-destructive. Automated firewall block rules, routing changes, and script executions are prohibited. All recommendations mandate human analyst validation (`analyst_validation_required = True`).

## 4. Deterministic Content Manifest & Identity Decoupling

### 4.1 Deterministic Content Manifest Hashing
To guarantee reproducible provenance across reruns, different core allocations, and Spark partition layouts:
1. All data files in the ingestion set are cataloged by their relative POSIX path.
2. The file list is sorted in ascending ASCII order.
3. Each file's content is hashed via SHA-256.
4. A canonical JSON structure `[{"path": p, "sha256": h, "size_bytes": s}]` is serialized with compact separators and sorted keys.
5. The `source_manifest_hash` is computed as `sha256(canonical_json)[:16]`.

### 4.2 Whole-File vs. Flow-Level Deduplication Policy
- **Whole-File Duplicate Detection:** Incoming files matching an existing file's SHA-256 hash in the manifest are flagged and discarded to prevent duplicate ingestion batches.
- **Flow-Level Handling:** Flows with identical numeric feature vectors (e.g., identical 64-byte SYN packets in a DDoS flood) represent valid physical network observations. Distinct flow records are **never** discarded merely because their feature values match.

### 4.3 Decoupled Identity Model
- **`profile_id` (Natural Key):**
  $$\text{profile\_id} = \text{sha256}(\text{source\_type} : \text{category\_id} : \text{window\_start} : \text{window\_end} : \text{window\_type})[:16]$$
  *Property:* Invariant across pipeline reruns and re-computations.
- **`snapshot_id` (Run-Specific Immutable Snapshot):**
  $$\text{snapshot\_id} = \text{sha256}(\text{profile\_id} : \text{run\_id} : \text{source\_manifest\_hash} : \text{schema\_version})[:16]$$
  *Property:* Unique to each execution run, capturing exact data and code provenance.

## 5. Multi-Metric Validation-Only Model Reliability Gating

Operational risk ratings and advisories must not rely on unverified or overfitted models. Reliability is evaluated **strictly on the validation split** (`val_predictions`); the final held-out test split is never used for operational policy tuning.

### 5.1 Configurable Decision Rules
- **Non-Evaluable (`NON_EVALUABLE`):**
  $$\text{Support}_{\text{val}} = 0$$
- **Unreliable (`UNRELIABLE`):**
  $$\text{Support}_{\text{val}} < 30 \quad \lor \quad \text{Any metric is missing (None)} \quad \lor \quad \min(\text{Precision}, \text{Recall}, \text{F1}) < 0.60$$
- **Evaluable (`EVALUABLE`):**
  $$\text{Support}_{\text{val}} \ge 30 \quad \land \quad \min(\text{Precision}, \text{Recall}, \text{F1}) \ge 0.60$$
- **High Reliability (`HIGH_RELIABILITY`):**
  $$\text{Support}_{\text{val}} \ge 100 \quad \land \quad \min(\text{Precision}, \text{Recall}, \text{F1}) \ge 0.75$$

## 6. Threat Level Risk Score (TLRS) Calculation Engine

### 6.1 Formula & Approved Component Weights
$$\text{TLRS} = w_{\text{sev}} S_{\text{sev}} + w_{\text{freq}} S_{\text{freq}} + w_{\text{rec}} S_{\text{rec}} + w_{\text{target}} S_{\text{target}}$$
$$\text{Weights:} \quad w_{\text{sev}} = 0.40, \quad w_{\text{freq}} = 0.25, \quad w_{\text{rec}} = 0.20, \quad w_{\text{target}} = 0.15 \quad (\text{Sum} = 1.00)$$

### 6.2 Component Scorers
1. **Severity ($S_{\text{sev}} \in [0, 100]$):** Class prior score based on domain impact (e.g., Infiltration = 90, Bot = 85, SQL Injection = 80, DDoS = 75, DoS = 65–70, Brute Force = 55–60, Benign = 0).
2. **Frequency ($S_{\text{freq}} \in [0, 100]$):** Logarithmic scaling:
   $$S_{\text{freq}} = \min\left(100.0, \max\left(0.0, \frac{\log_{10}(\text{flow\_count})}{\log_{10}(1{,}000{,}000)} \times 100.0\right)\right)$$
3. **Recurrence ($S_{\text{rec}} \in [0, 100]$):** Window-specific observation horizon:
   - **`full_campaign`:** Denominator $H = 8$ (the 8 distinct observed dates in CSE-CIC-IDS2018: Feb 14, 15, 16, 21, 22, 28, Mar 1, Mar 2; *not* 17 calendar days).
   - **`daily`:** Denominator $H = 24$ (active hours within the day).
   - **`hourly`:** Denominator $H = 12$ (active 5-minute intervals within the hour).
   $$S_{\text{rec}} = \min\left(100.0, \frac{\text{active\_observation\_units}}{H} \times 100.0\right)$$
4. **Target Impact ($S_{\text{target}} \in [0, 100]$ or None):** Destination asset criticality.

### 6.3 Missing Evidence Governance Policy
When host telemetry / destination asset criticality is missing (the reality of `flows.parquet`):
- `tlrs_complete = null`
- `evidence_coverage = 0.85` ($85\%$)
- `scoring_status = "insufficient_evidence"`
- **Diagnostic Partial Sum:**
  $$\text{TLRS}_{\text{partial}} = 0.40 S_{\text{sev}} + 0.25 S_{\text{freq}} + 0.20 S_{\text{rec}}$$
- **Normalized Heuristic Score:**
  $$\text{TLRS}_{\text{heuristic}} = \frac{\text{TLRS}_{\text{partial}}}{0.85}$$
- **Operational Rating Policy:** The operational `risk_band` is **withheld** as `"Insufficient Evidence"`. The heuristic rating is labeled as `provisional_risk_band = "DIAGNOSTIC_ONLY: <Band>"`.

### 6.4 Arithmetic Rounding and Risk Band Intervals
- **Rounding:** Arithmetic Round Half-Up: $\lfloor x + 0.5 \rfloor$.
- **Half-Open Intervals:**
  - $[0, 20)$: **Informational** (0 to 19)
  - $[20, 40)$: **Low** (20 to 39)
  - $[40, 60)$: **Medium** (40 to 59)
  - $[60, 80)$: **High** (60 to 79)
  - $[80, 100]$: **Critical** (80 to 100)

## 7. Explainable Defensive Advisory Recommendations

All recommendations adhere to strict governance rules:
1. `analyst_validation_required: bool = True` is mandatory on every recommendation record.
2. Actions are categorized into:
   - `Rate Limiting Review`
   - `Investigation`
   - `Telemetry Enrichment`
   - `Policy Hardening`
3. Explicit enrichment advisories are automatically generated when:
   - Target impact telemetry is missing (`ENRICH_ASSET`).
   - ML model reliability is `UNRELIABLE` or `NON_EVALUABLE` (`VERIFY_ML`).
